# Pruebas de frontend de CU01 y CU02

## Alcance y ejecución

Pruebas de componentes e integración del frontend con Vitest, jsdom y MSW. Se montan las pantallas y los servicios reales del cliente; las respuestas HTTP son simuladas. No se comprueban persistencia del backend, entrega de correos, precisión del NLP, bloqueo real de cuentas ni tiempos de servicios externos.

Desde `Desarrollo/KPB/Implementacion/Frontend`:

```bash
npm test -- src/features/auth src/features/chat --maxWorkers=2
npm run lint
npm run build
```

Con Node 26 se observó que Web Storage nativo interfiere con el localStorage de jsdom. Sin cambiar dependencias ni configuración del proyecto, ejecutar desde Bash (también Git Bash en Windows):

```bash
NODE_OPTIONS=--no-experimental-webstorage npm test -- src/features/auth src/features/chat --maxWorkers=2
```

En PowerShell, definir `$env:NODE_OPTIONS = '--no-experimental-webstorage'` antes del comando de npm. La opción debe llegar a los procesos de prueba: pasarla solamente al proceso inicial mediante `node --no-experimental-webstorage ...` no basta con este Vitest.

Los tests restablecen el estado, crean cachés independientes y usan manejadores locales con `server.use`. No requieren una API real. Los dos workers evitan saturar el equipo; no se ampliaron los timeouts para ocultar fallos.

## Defectos funcionales pendientes: cinco casos de fallo esperado

Los casos con prefijo **DEFECTO** usan `it.fails`: se ejecutan y comprueban el comportamiento correcto esperado, pero actualmente reproducen un defecto. Vitest los incluye como aprobados cuando fallan como se esperaba. **Un resultado verde no significa que estos defectos estén resueltos ni que ambos CU cumplan toda la documentación.** Al corregir la aplicación, retirar `.fails` conservando las mismas aserciones.

- **CU01, dos casos:** `ResetPasswordPage.tsx` muestra un mensaje de código inválido/expirado cuando el reset devuelve `PASSWORD_MISMATCH` o `PASSWORD_POLICY_VIOLATION`, en vez de explicar el error de contraseña. Regresiones en `passwordRecovery.test.tsx`.
- **CU02, un caso:** `TransactionPreviewCard.tsx` vuelve a insertar la categoría de la vista previa aunque esté inactiva y habilita aceptar. Regresión en `TransactionPreviewCard.test.tsx`.
- **CU02, dos casos de privacidad:** al recibir `SESSION_EXPIRED` durante extracción o guardado, se elimina el token y se redirige, pero el chat vuelve a escribir los mensajes privados en localStorage. Regresiones en `ChatPage.resilience.test.tsx`. La limpieza aislada de sesión se prueba por separado y funciona.

También persiste una diferencia de contrato: el CU02/API-06 documentado registra por `POST /transactions/text`, mientras la interfaz actual extrae por `POST /extractions/text` y confirma por `POST /transactions` con `source: "text"`. Estas pruebas preservan ese flujo actual; no certifican que coincida con el backend ni cambian las rutas para ocultar la diferencia.

## Resultado de referencia de esta ampliación

- CU01/CU02: **151 casos ejecutados**, sin pruebas omitidas; 146 comprobaciones satisfactorias y los cinco fallos esperados anteriores. Lint y compilación correctos.
- Comprobación adicional con `--maxWorkers=2 --sequence.shuffle --sequence.seed=20261104`: los mismos 151 casos, sin fallos inesperados (con `NODE_OPTIONS` indicado arriba).
- Suite completa: **159 aprobados (incluidos los cinco fallos esperados), ocho fallidos y dos errores no capturados**, los mismos fallos externos a CU01/CU02 observados antes de los cambios.
- Fallos preexistentes: dos en `mocks/historyHandlers.test.ts`, dos en `features/history/pages/HistoryPage.test.tsx`, dos en `features/notifications/services/notificationStream.test.ts`, uno en `mocks/walletBalanceHandlers.test.ts` y uno en `mocks/notificationHandlers.test.ts`. No se modificaron esos módulos ni sus pruebas.
